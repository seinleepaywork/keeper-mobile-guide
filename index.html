§0작업 개시 규칙

이 문서는 참고 자료가 아니라 착수 조건이다. 아래 순서를 밟지 않은 화면은 완료로 보지 않는다.

0.1언제 이 문서를 펴는가판단이 애매하면 해당하는 것으로 본다. 문서를 읽는 비용이 화면을 다시 만드는 비용보다 싸다.

필독

화면에 보이는 것을 새로 만들거나 고치면 전부 해당한다. 개발자와 Claude Code 모두에게 적용된다.

  • 신규 서비스·화면 추가 — 첫 줄을 쓰기 전에 §2에서 화면 유형을 고른다.
  • 기존 메뉴 개선 — 고치는 화면이 지금 어느 패턴인지 먼저 확인한다. 개선한다고 패턴을 바꾸지 않는다. 지시받은 곳만 고친다 — 규칙을 새로 받아도 지목한 곳만 고치고, 나머지는 앞으로 만들 때 그 규칙을 지킨다. 피그마나 이 문서가 정한 요소를 규칙 때문에 지우기 전에는 묻는다. 2026-09-25 에 두 번 어겼다 — 「여백 안에 여백」을 전수로 걷다가 통화 목록 To Do 띠까지 지웠고, 가운뎃점 규칙을 받자 앱의 가운뎃점 118줄을 고치려다 「내가 지시한 곳 이외에 가운뎃점 수정하지 말고」를 들었다.
  • 컴포넌트 신설 — 배지·태그·버튼이면 §1.5와 §5 금지 #02를 먼저 본다. 같은 역할의 컴포넌트가 이미 있으면 그것을 쓴다 — 탭은 통화 목록의 탭, 목록 안 분류·정렬은 「전체 · 1주일 · 최신순」 선택기, 통화 행은 통화 이력의 행, 상세 상단은 거래처 상세의 상단이다(2026-09-19 「탭 스타일 왜 저거 써놨어? 통화목록에서 잘 쓰던 거 있잖아」).
  • 레이아웃·밀도 변경 — §2 네 패턴(목록형 · 상세형 · 오버레이형 · 대화형) 밖으로 나가지 않는다. 다섯째 패턴을 만들지 않는다.
  • 통화 · To Do 상태 — 통화 내역 행 · 요약 카드 · To Do 에 상태 배지나 주 행동이 걸리면 §3 통화 라이프사이클을 그대로 쓴다. 새로 정하지 않는다.

0.2작업 순서는 이 순서로만

5단계
  1. 기기·맥락 확인 — 화면을 그리기 전에 한 줄로 적는다: 이 사용자는 어느 기기로, 무엇을 손에 들고, 어디서 이 화면을 여는가. PRD 의 버튼 이름을 그대로 옮기기 전에 그 기기에서 그 행동이 성립하는지 본다 — 통화가 끝난 직후 OS 화면 위에 뜨는 카드에서 성립하는 행동은 「AI로 요약받기」 하나다 — 파일 고르기 · 긴 입력은 그 시점에 없다(피그마 통화 종료 카드). 입력 경로는 그 기기에서 사용자가 이미 매일 하는 행동 위에만 놓는다.
  2. HQ 웹 화면은 이 문서로 검수하지 않는다. 웹 편(keeper-hqweb-guide)이 정본이다. 이 문서는 모바일 앱 화면만 담는다. 웹 편에 있던 모바일 괄호값은 2026-09-04 이 문서로 옮기고 웹 편에서 지웠다. 같은 규칙을 두 문서가 다르게 적는 순간 둘 다 못 믿는다 — 한쪽에서 지우고 다른 쪽에 적는다. 양쪽에 두지 않는다. 반대로 이 문서에는 웹 값이 없어야 한다 — scripts/check-mobile-scope.py가 웹 전용 용어를 훑어 빌드를 막는다.
  3. 트랙이 둘이면 뼈대를 나란히 적는다. 초보자용 · 전문가용처럼 같은 목적의 경로가 둘이면 단계 이름을 두 줄로 나란히 써서 1:1로 대응하는지 본다. 대응하지 않는 단계가 있으면 그것은 밀도 차이가 아니라 구조 분기다 — 사용자는 다른 제품을 두 개 쓰게 된다. 실측: 전문가 트랙의 첫 카드에 행동이 4개(초보자는 2개)였고, 「자료 없이」를 고르면 질문을 하나도 하지 않고 완결로 건너뛰었다. 학습 인터랙션이 통째로 빠졌는데도 화면은 그럴듯했다. 차이는 받는 자료의 종류 · 질문의 성격 · 문장의 밀도에만 둔다. 단계의 순서와 개수는 같다.
  4. 데이터 존재 시점 확인 — 화면에 넣는 모든 숫자·목록·이름에 대해 「이 사용자가 이 화면을 보는 시점에 이 데이터가 어디서 오는가」를 한 줄로 적는다. 답하지 못하면 허구다. 온보딩 화면의 지금 쌓인 일이 6건입니다는 첫 데모의 장식 문구였는데, 일곱 번 고치는 동안 아무도 묻지 않아 그 위에 실물 캘리브레이션 설문까지 세워졌다. 데모 데이터는 설계를 오염시킨다 — 존재할 수 없는 데이터로 채운 화면은 존재할 수 없는 흐름을 낳는다. 새로 가입한 계정에 예시 데이터를 섞지 않는다 — 통화가 찬 화면은 따로 로그인하는 계정으로 보여 주고, 새 계정은 비어서 시작한다. 「지금 보이는 통화는 예시예요」 같은 라벨로 때우지 않는다(2026-09-25).
  5. 기획 대조 — 스토리 · 스펙 목록을 받으면 항목마다 어느 화면의 무엇으로 되는지 한 줄씩 적고, 빠진 항목을 보고한다. 목록과 화면이 1:1 이 아니면 아직 시작하지 않은 것이다(2026-09-25 「스토리 내용은 전혀 반영을 안 했네?」).
  6. 첫 가입 흐름부터 — 가입이 끝난 상태를 전제로 화면을 만들지 않는다. 순서는 소개 → 권한 → 계정 → 약관 → 사업장 → 준비 완료다. 권한은 계정보다 먼저이고, 안드로이드는 전화 · 음성에 더해 다른 앱 위에 표시 · 통화 자동 녹음을 따로 받는다. 계정은 카카오 · 네이버를 앞에 두고 이메일은 작게 둔다. 온보딩은 이 흐름 자체를 그림으로 따라 하게 만드는 것이다 — 가입 뒤 튜토리얼 하나로 갈음하지 않는다(2026-09-25 「온보딩이 뭔지 몰라?」).
  7. 화면 유형 분류 — §2에서 정한다. 목록형이면 제목 + 세그먼트 칩 + 카드 리스트(행 72/95pt) + 하단 탭바, 상세형이면 뒤로 + 제목 + 탭 2개 + 본문 + 하단 고정 한 줄, 오버레이형이면 OS 화면 위 카드 모달(질문 1 · 주 행동 1 · 보조 1) 또는 풀스크린 시트, 대화형이면 제목 + 대화(첫 화면은 할 수 있는 일 → 추천 카드) + 떠 있는 입력창. 어느 쪽인지 말하지 못하면 아직 시작하지 않은 것이다.
  8. 통화 상태 확인 — 통화 내역 행 · 요약 카드 · To Do 가 관여하면 §3 표에서 상태별 표시와 주 행동을 그대로 가져온다. 색을 새로 만들지 않는다.
  9. §1 공통 헌법 적용 — 10개 조항을 전부 적용한다. 특히 §1.2 모달 내부 인풋 금지는 대체안(인라인 편집 · 풀스크린 시트 · 독립 화면) 중 하나를 먼저 고른 뒤 만든다.
  10. §5 금지 패턴 선탑재 — 금액 입력·배지·모달·비동기 버튼·긴 텍스트가 있으면 해당 방지책을 작성 단계에 넣는다. 리뷰에서 잡는 게 아니다.
  11. 입력 화면 상태표 작성 — 하단 입력창·고정 패널이 있으면 키보드 닫힘/열림 × 패널 최소화/확장 × 빈 입력/여러 줄 입력을 구현 전에 적는다. 어느 상태에서도 입력창과 현재 작업이 동시에 보여야 한다.
  12. 같은 것을 보여 주는 모든 곳을 함께 고친다 — 화면을 바꾸면 그 화면을 그린 튜토리얼 · 소개 그림과 사용 가이드 문구도 같은 변경에 넣는다. 숨기라는 지시는 같은 것이 보이는 모든 화면에 적용하고, 지우지 않고 한 곳의 스위치로 끈다 (2026-09-25 「왜 아직 남아있지?」 · 「왜 튜토리얼에 "오늘까지" 이거 남아있는건데」 · 「연관있는 화면들은 좀 알아서 고쳐라」).
  13. 완료 전 자기점검 — §0.4 체크리스트를 실측으로 확인한다. 눈대중은 통과가 아니다.

0.3규격에 없는 값을 만났을 때

Hard rule

규격이 비어 있는 지점부터 구현 편차가 시작된다. 추측한 값은 화면마다 달라지고, 다음 사람이 그걸 기준으로 또 추측한다.

Forbidden
  • 없는 값을 임의로 정하고 진행하기
  • 다른 화면에서 쓰는 값을 근거 없이 복사하기
  • "일단 이렇게 두고 나중에" — 나중은 오지 않는다
Do this
  • §7 미결 목록에 추가하고 사람에게 질문한다
  • 답을 못 받고 진행해야 하면 가정한 값을 명시한다
  • §7에 이미 있는 항목이면 그 결정을 먼저 받는다

§1모든 화면에 예외 없이 적용되는 공통 헌법

새 페이지나 컴포넌트를 만들 때 아래 10개 조항은 타협 대상이 아니다.

1.1무중단 흐름성공·저장 완료·복사 완료·네트워크 지연 모두 토스트로 전달한다. 닫기 클릭을 강제하지 않는다.

Non-disruptive
  • 작업 결과는 화면을 가로막지 않는 토스트로 전달하고 3초 후 자동 소멸시킨다.
  • 브라우저 기본 팝업 alert() confirm() prompt() 사용은 전면 금지.

1.2모달 제약 및 인풋 전면 금지앱 안에서 모달의 유일한 허용 목적: 영구 삭제 · 되돌릴 수 없는 발송 확정 같은 불가역 행동의 2버튼 확인. 예외는 OS 화면 위 카드 모달(통화 종료) 하나다 — 앱 화면이 아직 없는 시점의 유일한 표면이라 흐름을 끊는 것이 아니다.

Hard rule

모달 안 입력창은 작성 중 이탈 시 데이터 유실 · 뷰포트 스크롤 꼬임 · 모바일 키보드 가림을 유발한다. 설계 취향 문제가 아니라 시스템 차원에서 차단하는 항목이다.

Forbidden
  • 모달 다이얼로그 내부 <input> <textarea> <select> 구현
  • 모달 안 거래처 등록 · 메모 입력 팝업
  • 모바일의 오버레이는 둘이다 — 카드 모달과 풀스크린 시트. 피그마 실측. 카드 모달은 OS 화면(통화 종료 · 잠금) 위에 뜨는 한 장이다: 대상(번호/이름 + 태그) → 질문 한 줄 + 부제 → 주 행동 하나 → 보조 하나 → 캡션. 닫기는 우상단 텍스트. 풀스크린 시트는 내용이 긴 것(판단 근거) — 좌상단 ×, 세로 스크롤, 안에 카드 모달을 다시 띄우지 않는다. 바텀시트는 피그마에 없다. 쓰지 않는다(OPEN-16). 모달 안 입력 폼 금지는 웹과 같다. 카드 모달이 「불가역 확인」 규칙의 예외인 이유: 통화 종료 시점에는 앱 화면이 없다 — 카드가 유일한 표면이라 흐름을 끊는 것이 아니다. 앱 안에서는 여전히 불가역 확인에만 쓴다.
Use instead
  • 인라인 편집 — 체크리스트 항목 · 메모 한 줄처럼 단일·소량만 고친다
  • 풀스크린 시트 — 복합·보조 입력 · 긴 내용(판단 근거)
  • 독립 화면 — 거래처 등록 · 설정처럼 필드가 여럿인 입력
  • 이미 아는 값은 채워서 연다. 통화에서 온 전화번호처럼 앱이 아는 값을 다시 입력시키지 않는다(2026-09-11 「전화번호는 당연히 입력되있는 게 맞지 않아?」).

1.4타이포그래피 및 금융 데이터 표기

Typography
  • 한글·라틴은 Pretendard, 숫자는 Spoqa Han Sans Neo. 두 서체를 역할로 나눠 쓴다(2026-09-07 결정). 구현은 unicode-range 하나다 — 숫자 전용 @font-face에 unicode-range:U+0030-0039을 걸고 font-family 맨 앞에 둔다. 그러면 숫자만 Spoqa 에서 오고 나머지 글자는 다음 서체인 Pretendard 로 떨어진다. 순서가 바뀌면 분담이 조용히 깨진다 — 숫자까지 Pretendard 로 렌더되고 콘솔에는 아무것도 안 남는다. 명조(세리프)·필기체는 금지다.
  • 브랜드 정의서와 어긋난다. 브랜드 아이덴티티 가이드라인(2025-12-12판 p.21)의 지정 서체는 SUIT 다 — 이 문서가 쓰는 두 서체는 둘 다 그 지정이 아니다. 2026-09-07 사용자 지시로 Pretendard + Spoqa 를 쓴다. 브랜드 쪽 지정을 고칠지는 정해지지 않았다. 화면을 만들 때는 이 문서를 따르고, 인쇄물·오프라인 자산은 정의서를 따른다.
  • 쉼표·마침표는 넘기지 않는다. U+002C U+002E까지 숫자 face 에 넣으면 본문 모든 문장의 마침표·쉼표가 함께 바뀐다. 실측 폭이 다르다 — 쉼표가 Spoqa 0.189em · Pretendard 0.258em 이다. 금액의 쉼표는 Pretendard 에서 오지만, 한 열 안에서는 모든 행이 같은 서체를 쓰므로 우측 정렬이 그대로 맞는다.
  • 두 서체를 섞어도 단차가 없다(실측). x-height 는 Spoqa 0.543em · Pretendard 0.530em 로 차이가 16px 본문에서 0.2px, cap-height 는 0.733em 대 0.707em 로 0.42px다. 눈에 보이지 않는다. 단 줄 높이는 숫자로 못박는다 — Spoqa 의 ascent+descent 가 1.252em 로 Pretendard 1.193em 보다 커서, line-height를 비워 두면 숫자가 있는 줄만 미세하게 높아진다.
  • 웨이트 사다리는 400 / 500 / 700만 쓴다 — 두 서체의 교집합이다. Pretendard 는 100~900 이 전부 있지만 Spoqa 는 100·300·400·500·700 뿐이다. 600·800·900 을 쓰면 그 줄의 숫자만 다른 웨이트로 튄다 — 글자는 Pretendard 600 으로 가는데 숫자는 Spoqa 에 600 이 없어 브라우저가 대체한다. font-weight:600은 500 으로 내린다.
  • 코드·토큰 문자열만 시스템 모노(ui-monospace)를 허용한다. 본문 서체로 코드를 쓰면 열 정렬이 깨진다. 웹폰트는 추가하지 않는다.
  • 모든 텍스트 컨테이너에 word-break: keep-all overflow-wrap: break-word (웹뷰: Tailwind break-keep · 네이티브 대응은 OPEN-17).
  • 금액·수량·세액 셀은 font-variant-numeric: tabular-nums + text-right + 3자리 콤마(1,250,000원).
  • 숫자 고정폭은 Spoqa 가 준다. 실측: Spoqa 숫자는 열 글자가 모두 596/1000em 으로 같고, Pretendard 숫자는 비례폭이다(Regular 에서 1 898/2048em · 0 1220/2048em 등 아홉 가지). 그래서 숫자를 Spoqa 에서 가져오면 tnum 없이도 표가 정렬된다. font-variant-numeric: tabular-nums 선언은 그대로 유지한다 — Pretendard 에는 tnum 이 실제로 있고, 두 서체가 모두 없는 폴백 환경에서 필요하다. 브라우저 실측(16px · 이 페이지): Pretendard 기본은 1 7.02px · 0 9.53px 로 어긋나고, tnum 을 켜면 둘 다 9.83px 로 맞는다. Spoqa 는 선언 없이도 둘 다 9.55px 다.
  • 본문은 컨테이너 폭을 채운다검증은 Range.getClientRects()로 한다. 인라인 박스의 세로 중심을 line-height의 60% 오차로 묶어야 한다 — top으로 묶으면 code의 패딩 때문에 한 줄이 둘로 세어진다. — 마지막 줄을 제외한 모든 줄에서 남은 공간(콘텐트박스 오른쪽 끝 − 그 줄의 오른쪽 끝)이 다음 줄 첫 「끊을 수 없는 단위」(어절, 또는 nowrap 인라인 요소 전체)의 폭보다 좁아야 한다. 그보다 넓으면 들어갈 수 있는 어절을 못 넣은 것이므로 폭 상한이나 줄바꿈 설정이 잘못된 것이다. 퍼센트로 판정하지 않는다 — 실측 결과 keep-all 한글 열에서는 88%가 물리적 최대인 문장이 존재한다(341px 열). 마지막 줄이 짧은 것은 좌측 정렬에서 정상이며, 한 음절만 남으면 결함이다 — 문장 길이를 고쳐서 막는다.
  • 한글 폭을 ch로 재지 않는다. ch는 0 글리프 폭 기준이고 Spoqa 0.596em · Pretendard 0.5957em 으로 두 서체가 사실상 같다. 한글은 1em 이 아니다 — 실측 Pretendard 0.864em · Spoqa 0.920em 이다. 그래서 max-width:46ch는 한글 약 32자 — 의도한 46자의 69%다. 폭 상한이 필요하면 em이나 px로 지정한다.
  • text-wrap은 본문에서 auto로 둔다. balance는 가장 긴 줄을 줄여 모든 줄을 짧게 만든다. pretty도 마찬가지다 — 2~3줄짜리 짧은 문단이면 폭과 무관하게 첫 줄을 줄인다. 웹 편 실측(문서 열)에서 pretty가 1줄에 151px을 남기고 다음 어절을 내렸다(341px 열에서는 [255,103] → auto [300,59]). 외톨이 마지막 줄은 CSS로 막지 않고 문장 길이로 막는다. balance는 2~3줄 표제에만 쓴다.
  • 짧은 의미 단위는 쪼개지 않는다 — 조항 참조(§0 작업 개시 규칙) · 수치+단위(72pt) · 금액(1,250,000원) · hex(#F9FAFB)는 white-space: nowrap으로 묶는다. 공백 포함 14자까지만 — 그보다 길면 묶지 않는다. 좁은 화면에서 넘친다. 코드 토큰을 묶을 때는 code.tok.keep 처럼 구체성을 맞춘다 — .keep(0,1,0)은 code.tok(0,1,1)에 밀려 조용히 무시된다(실측). 단 표 · 코드 블록처럼 가로 스크롤 컨테이너 안에서는 길이와 무관하게 묶는다 — 넘침이 스크롤로 처리되므로, 쪼개면 오히려 좁은 셀에서 세로로 흐른다(웹 편 실측: 좁은 표 셀 158px에서 2.6자/줄).
  • 선택지는 세로로 한 줄에 하나씩 놓는다. 가로로 나란히 놓지 않는다. 웹 편에서 두 번 틀렸다 — ① grid-auto-columns:1fr로 등분하니 412px 열에서 한 칸이 85px이 되어 외상 … 1,00…으로 네 개 다 잘렸다. ② 잘림만 막으려고 flex-wrap으로 흘리니 2×2 격자가 됐다 — 읽는 방향이 둘이 되고 항목마다 폭이 달라 같은 층위의 선택지가 달라 보인다. flex-direction: column으로 쌓으면 폭이 모두 같고, 라벨이 잘릴 일이 없고, 눈은 아래로만 내려간다. 가로 묶음은 「확정 · 넘어가기」처럼 성격이 다른 두 동작에만 쓴다.
  • 고를 대상과 제목은 자르지 않는다. 선택지 · 버튼 · 탭 · 목적지 이름 · 화면 제목에 text-overflow: ellipsis를 걸면 무엇을 고르는지 모르는 채로 고르게 된다. 말줄임은 읽지 않아도 되는 것(로그 · 경로 · ID)에만 허용한다.
  • break-keep은 단어 안을 보호할 뿐, 구(句)가 줄바꿈으로 쪼개지는 것은 막지 못한다. 금지 #05의 방지책만으로는 부족하다.
  • 한글에 양수 letter-spacing을 주지 않는다. 대문자 라틴 라벨의 관습(letter-spacing:.1em)을 한글에 옮기면 시 작 하 기처럼 자간이 벌어져 단어가 흩어진다. 한글은 0 또는 음수만 쓴다 — 제목은 -0.015em 정도로 조인다. 양수 자간은 라틴 대문자 라벨에만 허용한다.
  • 크기는 사다리에서만 고른다. 아래 표 밖의 크기를 쓰지 않는다. 여섯 단은 피그마 「키퍼 AI 통합 ver」에서 실측한 값이고 본문·라벨은 그 값에서 파생했다. 재는 방법: 렌더 이미지의 잉크 높이를 재고, 같은 글자를 Pretendard 로 직접 렌더해 얻은 잉크/글자크기 비율(한글 Bold 0.890 · 라틴 Bold 0.715)로 나눴다. 오차 ±1.5pt.
  • 모바일은 제목·라벨에 700 을 쓴다. 웹 편은 h3 아래를 500 으로 두지만, 피그마는 리스트 행 제목·체크리스트 항목·보조 버튼 라벨까지 전부 700이다 — 작은 화면에서 500 은 위계가 안 선다. 500 은 입력 라벨과 탭에만 남긴다.
  • 본문은 16pt 아래로 내리지 않는다. 손에 든 기기에서 15pt 미만은 읽는 자세를 바꾸게 한다. 가장 작은 값은 11pt이고 캡션·부제·시각까지다. 그 아래는 만들지 않는다.
  • pt(iOS) = dp(Android) = CSS px 1:1 이다. 그래서 아래 견본은 실제 크기다 — 이 문서를 100% 배율로 보면 폰에서 보이는 크기와 같다. 구현 스택별 단위 대응은 OPEN-17.
  • 행간은 숫자로 못박는다. 숫자가 Spoqa 에서 오고 그 지표가 Pretendard 보다 커서, 비워 두면 숫자가 있는 줄만 높아진다. 목록 행의 높이(72pt · To Do 포함 95pt)는 행간이 아니라 행 규격이 정한다(§0.4).
  • 기기 글자 크기를 막지 않는다. 사장님은 시스템 글자를 키워 쓴다. 글자 크기를 막거나(maxFontSizeMultiplier · allowFontScaling={false}) 줄이지 않고, 기본 디자인도 바꾸지 않는다. 배율이 1보다 클 때만 레이아웃이 자리를 내준다 — 한 줄로 자르던 이름은 두 줄까지, 부제 줄은 줄바꿈, 필터 줄은 둘째 줄로, 고정 높이 면(탭바)은 늘어난 줄 높이만큼 키운다. 배율 1에서는 기본 디자인과 픽셀까지 같아야 한다. 확인은 1.3배 · 1.6배다 (2026-09-25 「폰트크기를 통제하거나 기본디자인을 바꾸라는 얘기가 아니라 어떻게 좀 못하나?」).
  • 대메뉴 탭 화면의 제목은 모두 같은 값이다. 한 탭만 작으면 다른 제품처럼 보인다(2026-09-25 「거래처 헤더타이틀 뭔가 더 작은 거 같다?」). 값은 OPEN-19.

1.5표면과 깊이감(인터콤 서피스 언어)

Surface

그림자로 층을 만들지 않는다. 배경과 카드의 미세한 명도 대비 + 1px 헤어라인으로 분리한다.

  • 회색 캔버스 위에 흰 카드가 라운드로 떠 있는 구조다. 카드를 화면 좌우 끝까지 채우고 선으로만 가르는 것은 인터콤이 아니다 — 좌우 20pt 여백으로 배경이 카드 바깥에 보여야 한다(피그마 실측).
  • 탭바·헤더 배경에 브랜드 원색을 채우지 않는다. 피그마의 하단 탭바는 흰 면 + 어두운 아이콘·라벨이고 활성만 #00CC46이다(OPEN-13). 짙은 색으로 채운 바는 다른 제품의 언어다. 통화 중 오버레이의 다크 배경은 OS 통화 화면을 따른 것이라 예외다.
  • 여백은 타이트하다. 리스트 행은 72pt(To Do 포함 95pt)로 한 행에 다섯 가지(방향 · 이름 · 부제 · 척도 · 시각)를 담고, 카드 안 요소 사이는 좁다. 카드 사이 간격은 정밀 재측정 대상이다(OPEN-16). 넓은 것은 섹션 사이뿐이다 — 구분선 + 큰 간격으로 덩어리를 가르고, 덩어리 안은 붙인다. "타이트한 행 + 넓은 섹션 간격"이 인터콤의 리듬이다.
  • 섹션은 카드로 가르지 않는다. 라벨 + 1px 구분선만으로 가른다. 카드는 성격이 다른 묶음에만 쓴다.
  • 섹션 위에 라벨을 얹지 않는다. 제목 위에 시작하기 같은 작은 라벨(eyebrow)을 두면 바로 아래 제목과 같은 말을 두 번 하거나, 정보가 없는 장식이 된다. 섹션은 제목 + 위쪽 구분선으로 충분하다. 상태·개수처럼 정말 필요한 보조 정보는 제목과 같은 줄 오른쪽에 붙인다.
  • 장식 도형을 붙이지 않는다. 라벨·제목 앞의 사각(■)·점·아이콘 같은 장식은 정보를 담지 않으면서 시선을 끈다.

Layout integrity

지표 한 칸에는 값 하나만 넣는다. 큰 숫자 옆에 다른 지표를 붙이면 무엇이 주 값인지 사라진다.

Forbidden
  • 한 칸에 지표 둘 — 6건 합계 35,328,000원
  • 성격이 다른 지표를 같은 행에 나열 — 업무량(건수·금액)과 소요 예측(3분)은 다른 종류다
  • 큰 값 뒤에 작은 라벨을 같은 줄에 붙여 위계를 뭉개기
  • 1열 · 좌우 20pt · 카드 라운드 16pt(리스트) / 12pt(체크리스트) / 20pt(카드 모달). 피그마 실측(±1.5pt). 안전영역: 상단 상태바 아래에서 콘텐츠 시작, 하단 홈 인디케이터 34pt 위로 고정 요소를 올린다 — 하단 고정 CTA는 프레임 하단에서 40pt, 하단 탭바 흰 면은 53pt(탭 + 인디케이터 여백, 실측). 키보드가 올라오면 입력 영역은 줄어든 가시 뷰포트의 하단에 붙고, 스크롤 본문은 입력 영역 높이만큼 하단 여백을 확보한다. 키보드 위에 입력창을 절대 좌표로 겹쳐 놓지 않는다.
Do this
  • 한 칸 = 라벨 하나 + 값 하나
  • 지표 행은 같은 종류·같은 단위만 묶는다
  • 종류가 다르면 행을 나누거나 문장으로 쓴다
  • 같은 행에 놓인 컨트롤은 높이가 같다. 한 행의 컨트롤은 행 높이 토큰 하나(--row)를 나눠 쓴다 — 각자 자기 높이를 들고 오면 단차가 난다. 웹 편 실측: 대화 입력줄에 첨부 버튼 40px · 입력창 42px · 보내기 44px이 한 줄에 놓여 있었다. 아래 끝만 맞추고 위 끝이 세 층으로 어긋났고, 모서리도 9px · 10px가 섞였다. 같은 카드의 행동 버튼도 44px 옆에 40px이 있었다. 원인은 각 컨트롤이 자기 height를 갖고 있었던 것, 그리고 입력창의 자동 높이가 placeholder 줄 수까지 세고 있었던 것이다. 고치는 법: 높이는 토큰에서만 받고, 입력창은 줄높이 + 패딩 + 테두리 = 행 높이가 되게 패딩을 행 높이에서 계산하고, 빈 칸은 재지 않고 행 높이로 둔다. 여러 줄로 자란 입력창만 예외다 — 그때도 나머지는 그 아래 끝에 맞춘다(align-items: end). 행 높이 토큰은 44pt다 — 바꿀 때도 토큰 하나만 올린다. 한 행이 같이 자란다. 대신 그 안의 글자 길이가 제약된다 — 한 줄 높이의 입력창에 두 줄짜리 플레이스홀더를 넣으면 둘째 줄이 잘린다(§1.10).
  • 같은 컬럼의 모든 블록은 좌우 끝이 정확히 일치한다. 실측으로 확인한다 — 컬럼 안 블록들의 left 값이 하나여야 하고, right 값도 하나여야 한다. 카드 내부 요소는 카드 패딩만큼 들어가는 것이 정상이다.
  • 텍스트를 짜부라뜨리지 않는다. flex 한 줄에 줄지 않는 형제(번호 · 배지 · 아이콘 — flex-shrink:0이 기본 탑재다)와 텍스트를 나란히 두고 텍스트에 min-width:0을 걸면, 폭이 줄 때 텍스트가 감소분을 전부 흡수한다. 실측: 미결 항목 헤더 [번호][제목][배지]를 flex-wrap:nowrap + min-width:0으로 두자 헤더 182px에서 제목 47px, 152px에서 17px(12줄), 122px에서 0px(14줄) — 규 격 의 적 용 범 위처럼 한 글자씩 세로로 흘렀고 가로로 85px 넘쳤다. 텍스트에는 최소 폭을 남기고(flex:1 1 14em; min-width:12em) 폭이 부족하면 형제를 다음 줄로 내린다(flex-wrap:wrap). 최소 폭은 부모 폭을 상한으로 둔다 — min-width:min(12em,100%). 12em을 고정하면 부모가 그보다 좁을 때 카드 밖으로 78px 삐져나온다(실측). 금지 #02의 방지책은 배지·태그·버튼에만 걸려 있었다 — 같은 붕괴가 제목에서 다시 났다. 텍스트도 대상이다.
  • 번호 · 코드 라벨은 제목의 일부로 넣는다. §1 1.9 OPEN-06 같은 앞머리를 제목의 형제로 두면 두 가지가 동시에 발생한다 — 폭이 좁아지면 제목 위로 접혀 eyebrow가 되고(§1.10 금지), 접히지 말라고 nowrap을 걸면 제목이 짜부라진다. 둘 다 막는 방법은 하나다 — 번호를 h3 안의 앞머리 span으로 넣는다. 제목 안에 있으면 접힐 형제가 없고 짜부라뜨릴 형제도 없다.
  • 브라우저 기본 여백을 리셋에서 빠뜨리지 않는다. <ol>은 padding-inline-start: 40px이 기본값이다. ul만 리셋하면 ol 행 하나가 40px 밀려 좌우 단차가 생긴다. ul,ol,dl,dd,figure,fieldset을 함께 리셋한다.
  • 콘텐츠가 뷰포트를 채운다. 첫 화면에서 빈 공간이 세로 40%를 넘으면 화면 유형 분류(§2)가 틀린 것이다.
  • 그룹 간 간격은 그룹 내 간격의 2배 이상. 선택 옵션들 사이가 8px 인데 옵션과 주 CTA 사이가 6px 이면 둘이 한 덩어리로 읽힌다. 간격이 위계를 만든다 — 색만 바꿔서는 분리되지 않는다.
  • 같은 행의 컨트롤은 오른쪽 끝을 맞춘다. 내용 폭으로 두면 옵션 3개의 끝이 439·545·633px 처럼 다 달라진다. 선택 그룹은 flex:1 또는 grid 로 균등 분할하고, 주 CTA 는 그룹과 같은 폭으로 두거나 명시적으로 좌측 정렬한다.

  • 보이는 컨트롤은 동작한다. 눌러도 아무 일이 없는 필터 · 정렬을 두지 않는다. 다른 경로(입력창의 답 등)로 정렬 · 필터가 바뀌면 그 컨트롤의 표시도 같이 바뀐다 — 목록은 「돈냄새순」인데 정렬 버튼은 「최신순」이면 둘 중 하나가 거짓이다(2026-09-16).

  • 읽는 문서의 문장 안에 클릭 대상을 심지 않는다. 인라인 링크의 히트 영역은 line-height(≈27px)를 넘길 수 없어 터치 타깃 40px 을 물리적으로 못 맞춘다(§1.5). 근거 조회·상세 열기 같은 행동은 문서가 아니라 대화나 별도 액션 행에 둔다.

§4의도적 차이 vs 정리 후보

다르게 생긴 화면은 두 종류다. 정당한 분기이거나, 아직 못 갚은 부채다. 섞어두지 않는다.

의도적 차이

웹 편과 정당하게 다른 것
  • 페이지 배경 — 모바일 #F1F3F5(피그마 실측), 웹 #F9FAFB. 같은 브랜드, 다른 매체. 값은 한 문서에 하나씩만 산다.
  • 밀도 — 웹은 표와 36–40px 행, 모바일은 카드 리스트 72/95pt. 표를 모바일로 옮기지 않는다.
  • 라운드 — 웹 12px 단일, 모바일 16 / 12 / 20pt 세 단계(리스트 · 체크리스트 · 카드 모달).
  • 상태 — 웹은 마우스 올림 상태가 있고 모바일은 없다. pressed · 선택 · 비활성 셋.
  • 오버레이 — 웹은 우측 시트, 모바일은 카드 모달 + 풀스크린 시트. 바텀시트는 어느 쪽에도 없다.
  • 단위 — 이 문서는 pt(iOS) = dp(Android) 논리 단위로 적는다. CSS로 적은 규칙(keep-all · tabular-nums 등)은 「무엇을 보장하는가」로 읽는다 — 스택별 대응은 OPEN-17.

정리 후보

피그마와 규격의 충돌 · 빈 곳
  • CTA 색 — 피그마 #00E235 + 흰 글자(1.76:1). Navy 채움으로 갈지 결정 대기(OPEN-12). 결정 전 구현은 §1.6 Navy.
  • 의미 색 넷 — 점수 주황 · 수신 파랑 · 수준 라벨 · 액센트 녹색(OPEN-13). 보조 글자 #939397는 3.06:1로 본문 크기에서 못 쓴다.
  • 선택칩 진한 채움 — #28272F + 흰 글자. §1.6 「선택 상태 채움 금지」와 충돌(OPEN-14).
  • 축 이름 — 피그마 「수요 의향」 vs PRD 「구매 의향」(OPEN-15). 한 이름으로.
  • 없는 화면 — 빈 · 로딩 · 에러 · 가로 · 부재중의 행동 · 「나중에」 이후 재요청(OPEN-16). §1.8 값은 웹 승계다. 키보드는 별도 화면이 아니라 §2의 공통 동작 규칙으로 검수한다.

# Z to Sigma (KeeperAI) Mobile Frontend Constitution & Rules

## 0. Before You Start (READ THIS FIRST)
- TRIGGER: any new screen/service, any menu improvement, any new component, any layout or
  density change, any transaction-document UI. If it renders, this applies.
- Do NOT write UI code before you have (a) picked the screen pattern and (b) read §1 of the UX guide.
- Order: 1) classify screen type → 2) lock document state badges/CTA → 3) apply the 5 constitution
  rules → 4) pre-load the incident guards → 5) verify the self-check list by measurement.
- If a spec value is MISSING: never invent one. Add it to the open-items list and ask.
  If you must proceed, state the assumed value explicitly in your report.
- Report must state: which screen pattern, which rule sections applied, which values you assumed.
- 전문: docs/UX_GUIDE.md §0. 이 절은 그 요약이다.

- When two tracks serve the same goal (novice / expert), write their step names side by side and check
  they map one to one. A step that has no counterpart is not a density difference, it is a structural fork — the
  user ends up with two different products. Measured: the expert track's first card carried four actions where the
  novice one had two, and its "no data" branch skipped every question and jumped to completion, dropping the whole
  learning interaction while still looking plausible. Differ only in the material you take, the nature of the questions,
  and sentence density. The order and count of steps stay the same.
- For every number, list or name on a screen, write one line: where does this data come from at the
  moment this user sees this screen? If you cannot answer, it is fiction. An onboarding greeting said "6 tasks
  waiting" for seven revisions before anyone asked — and a whole survey was built on top of it. Demo data corrupts
  design: a screen filled with data that cannot exist produces flows that cannot exist.
- Before drawing anything, write one line: which device, holding what, where is this user when
  the screen opens. Do not copy a PRD button name until the action holds at that moment on the phone — on the card over
  the OS screen right after a call exactly one primary action holds ("AI로 요약받기"); file pickers and long typing do
  not. Put input paths only on things the user already does daily on that device.

- Change only what you were told to change. A new rule governs new work; never retro-sweep the app with it, and
  ask before removing an element that Figma or this guide defines (the call-list To Do band was removed once and restored).
- When a screen changes, change every place that depicts it in the same change: tutorial and intro pictures, usage
  guide copy. A "hide" request covers every surface that shows the same thing, through one switch. Never delete.
- Start from a fresh signup: intro → permissions (incl. Android draw-over-apps and call recording) → account
  (Kakao / Naver first, email small) → terms → business → ready. Permissions come before the account. Never mix sample
  data into a new account; the populated account is a separate login.
- Before reporting done, confirm the build the user receives (the device bundle) contains the change.

## 1. Absolute Constraints (Zero Tolerance)
- FORBIDDEN: NEVER build form controls (`<input>`, `<textarea>`, `<select>`) inside Modal Dialogs.
- In-app modals are strictly for two-button confirmation of irreversible actions (Delete, Send-for-real). The one
  exception is the post-call card over the OS screen (§1.2): the app has no screen yet, so the card is the surface.
- For form inputs, use: (1) Inline editing (a checklist item, a one-line memo), (2) Full-screen sheets, or
  (3) Dedicated screens. No bottom sheets — none in Figma (OPEN-16).
- NEVER use system blocking alerts. Use Toast notifications (auto-dismiss 3s); irreversible confirms use the card modal.

## 2. Korean Typography & Numeric Rules
- All Korean text containers MUST include `word-break: keep-all; overflow-wrap: break-word;` (web view: Tailwind `break-keep`; native equivalents are OPEN-17).
- `break-keep` protects inside a word only. It does NOT stop a phrase from splitting across
  lines, and it does nothing about line fill.
- Body text MUST fill its container. Test per line: content-box right edge - line right edge
  must be SMALLER than the width of the next line's first unbreakable unit (a word, or a whole `nowrap` inline element
  such as `code`) plus one space advance. Never judge by percentage — in a keep-all Korean
  column 88% can be the physical maximum. A short last line is normal; a single-syllable last line is a defect, and you
  fix it by rewriting the sentence, not with CSS.
- NEVER measure Korean measure in `ch`. `1ch` is the width of `0`: 0.596em in Spoqa and
  0.5957em in Pretendard, practically the same. A Hangul glyph is not 1em — measured
  0.864em in Pretendard, 0.920em in Spoqa. So `max-width:46ch` yields about 32 Korean characters, 69% of what you
  intended. Use `em` or px.
- NEVER use `text-wrap: balance` or `pretty` on body text. Both shrink lines: balance shrinks the
  longest, pretty shrinks the first line of any 2-3 line paragraph. Use `text-wrap: auto`. Balance is for 2-3 line headings only.
- When asking a user for their own priorities, ask facts first, then have them rank real items.
  Never pose hypothetical dilemmas (`물건이 모자랄 때 누구 것부터?` — the honest answer is "it depends"; forcing three
  buttons loses the information and feels fake). Order it like a new bookkeeper's first day: what the business is, how
  money comes in, the delivery cycle — then rank real items. Never invent the items: if the
  screen has none yet (onboarding), get them from the user — have them name the clients they know and pick only among
  those names. A priority with nothing to order is deferred to the first real tasks: "when work
  arrives I will propose an order and ask you about the first few". Ranking real items beats hypothetical trade-offs; buttons beat numeric scales for
  non-experts. Do not fix the question count — ask what needs asking, silently skip what an earlier answer made moot.
  Users who gave files still get asked — data tells you facts, not judgment — but never ask what
  the files already say. Derive axes from the domain's top risk, not from the scoring formula. When the user hands you
  a list of items (purchase intent, specificity, timing, authority, size), that list IS the survey:
  keep the given names as the card titles, translate only the question sentence into the owner's words ("how do you tell
  a real buyer?"), and make the options the things they actually look at. Never reinterpret the list as "axes" — do not
  split an item into two questions, and do not keep old questions underneath. Doing so turned five items into nine and
  none of the given names appeared on screen. The list and the screen must match one to one.
  Data does not change the items. "Upgrade the questions with situations drawn from the submitted
  material" means fill each item's sentence and options with that material — not swap the items for new questions.
  Broken a second time in this document: when a ledger or files arrived, the five items became three new questions, and
  only the user's "is this actually fixed?" caught it. Check: with and without data, item names, order and card titles
  are identical; only the sentences differ.
- NEVER write copy that describes the screen: counting visible items ("둘 중 하나", "네 칸 중 1칸 채움"),
  restating an adjacent button ("건너뛸 수 있음" next to a skip button), or duplicating another indicator on the same
  screen. Delete test: if you cannot say in one sentence what the user stops knowing, leave it deleted.
- Stack choices vertically, one per line (`flex-direction: column`). Never lay options out
  side by side. Two failed attempts: equal grid columns gave each of four options 85px in a 412px column (web edition), so all four
  truncated to `외상 …` `1,00…`; then `flex-wrap` turned them into a 2x2 grid, which gives the eye two scan directions and
  unequal widths for items of equal rank. A column makes every option the same width, never truncates, and reads
  downward only. Horizontal grouping is only for two actions of different kinds (confirm / skip).
  Verify: distinct `getBoundingClientRect().top` values in one option list == number of options.
- Never let text be squeezed. In a flex row, siblings that do not shrink (numbers, badges, icons
  carry `flex-shrink:0` by default) push the whole reduction onto the text if the text has `min-width:0`. Measured: an
  item header `[number][title][badge]` with `flex-wrap:nowrap` gave the title 47px at 182px, 17px (12 lines) at 152px,
  and 0px (14 lines) at 122px — one Hangul character per line, overflowing by 85px. Leave the text a floor
  (`flex:1 1 14em; min-width:12em`) and let the siblings wrap. The badge-only guard from incident #02 never covered
  headings, so the same collapse came back there.
- Put numbers and code labels inside the heading, never beside it:
  `
1.9Title
`. As a sibling it either folds above the title (an eyebrow, forbidden
  by §1.10) or, once pinned with `nowrap`, squeezes it.
- Measure portrait only, at 402pt and 375pt, plus the width where that container is
  actually narrowest. Two are not enough — a header that passed at both edges collapsed below 182px (web edition).
- A placeholder must fit one line at the narrowest width. The input is one row tall
  (`--row`, 44pt) by the row rule, and an auto-growing box grows for its *value*, never for its placeholder — so a
  two-line placeholder has its second line clipped. Measured: at 375px the inner width was 151px while the placeholder
  ran 234px. Guidance that does not fit belongs in the question card, which has width.
- Keep the placeholder short and constant: name what the field takes (`말씀해 주세요`), not what
  to say. Changing it per state makes it long and repeats what was just said.
- Rules force values on each other: pinning a row height also pins the text length inside it.
  When you add a rule, write down what it constrains elsewhere. These collisions surface only by measurement — three
  times in this document (nowrap vs squeeze, min-width vs spill, row height vs text length).
- Controls in one row share one height. Take it from a single row token (`--row`); never let
  each control carry its own `height`. Measured (web edition): an attach button at 40px, a textarea at 42px and a send button at 44px
  sat in one composer row — bottoms aligned, tops stepped three ways, radii mixed 9px/10px; a card's action row had 44px
  next to 40px. Fix: `line-height + padding + border == row height` for inputs (derive padding from the token), and an
  empty textarea is set to the row height, not measured (placeholder lines inflate `scrollHeight`). The only exception
  is an input grown to several lines — then the others align to its bottom edge. The row
  token here is 44pt; raise the token alone so the whole row grows together. Verify: one distinct height/top/bottom per control row.
- NEVER truncate what the user must read to choose: options, buttons, tabs, nav labels, titles.
  `text-overflow: ellipsis` there hides the choice itself. Ellipsis is only for text nobody needs to read (logs, paths,
  IDs). Truncation appears only at some widths — count the declaration, not one screenshot.
- Wrap short semantic units in `white-space: nowrap`: section refs (`§0 작업 개시 규칙`), number+unit (`72pt`),
  money (`1,250,000원`), hex (`#F9FAFB`). 14 characters max, spaces included — longer units
  must be allowed to break or they overflow narrow screens.
- Two typefaces, split by role (decided 2026-09-07): Pretendard for Hangul and Latin, Spoqa Han
  Sans Neo for digits. Both SIL OFL 1.1. No serif/cursive fonts.
- The split is one mechanism: give the digit `@font-face` `unicode-range:U+0030-0039` and put it
  first in `font-family`. Digits then come from Spoqa and everything else falls through to
  Pretendard. Reorder the list and the split breaks silently — digits render in Pretendard
  and nothing is logged. Do NOT extend the range to `U+002C`/`U+002E`: that would move every sentence period and
  comma to the digit font too.
- Digits are fixed-width because Spoqa provides them: all ten are 596/1000em (measured), while Pretendard digits are
  proportional (`1` is 898/2048em, `0` is 1220/2048em). Keep the `tabular-nums` declaration anyway for fallback.
- Weight ladder is 400 / 500 / 700 only — the intersection of the two families. Pretendard
  ships 100-900 but Spoqa has only 100/300/400/500/700, so a 600 heading renders its digits at a different weight.
  Map `font-weight:600` to 500.
- Pin `line-height` numerically. Spoqa ascent+descent is 1.252em against Pretendard 1.193em, so a line containing
  digits grows slightly taller when line-height is left to the font.
- Only code/token strings may use `ui-monospace`. Never add another webfont.
- NEVER apply positive `letter-spacing` to Hangul. Copying the uppercase-Latin convention
  (`letter-spacing:.1em`) scatters Korean words into `시 작 하 기`. Use 0 or a negative value; headings tighten to
  about `-0.015em`. Positive tracking is for uppercase Latin labels only.
- Financial numbers in cards/lists MUST use `font-variant-numeric: tabular-nums`, right alignment (`text-right`),
  and 3-digit commas (`1,000,000원`).

## 3. Zero Clutter & Progressive Disclosure
- NEVER render multi-line static explanatory text directly under labels.
- Secondary descriptions MUST be wrapped inside a 16px `HelpCircle` icon triggering a Tooltip or Popover.

## 4. Visual Tokens & Surface Language
- Page Background: `#F1F3F5` (Figma, measured). Pure white `#FFFFFF` for page background is prohibited.
- Cards & Surfaces: `#FFFFFF`, radius 16pt (list card) / 12pt (checklist card) / 20pt (card modal). Border presence
  is unverified in Figma (OPEN-16). Drop shadows minimal — only the floating chat composer casts one
  (`0 4 12 #101828 10%`, Android elevation 6), with no background band around it.
- No box inside a card: never put a filled, bordered or re-padded box inside a padded card. Inputs sit on the canvas
  (white, 1pt hairline, Navy focus). The call-list To Do band is the one exception.
- Nested cards: the OUTER radius MUST equal `inner radius + the gap between the two surfaces`. Equal radii
  misalign the two arcs and the outer corner reads as pinched. This is geometry, so it holds regardless of unit or
  platform; it was measured in the HQ web edition (inner `12px` inset `16px`, outer raised to `12 + 16 = 28px`).
  The `16 / 12 / 20pt` above are SINGLE-surface values. Repeat the formula per nesting level, keep the gap and the
  radius as separate tokens with the derivation in a comment, and skip the rule where no inner card exists.
  Whether the three Figma-measured radii satisfy this in real nesting is not yet measured (OPEN-18).
- Touch Targets: minimum height 44pt; primary CTA 51pt; checklist rows 44pt (Figma, measured).
- Badges & Tags: Always set `flex-shrink: 0; white-space: nowrap;` to prevent layout collapse.
- Light theme ONLY. Declare `color-scheme: light`. Never add a dark palette or `prefers-color-scheme` block.
- Brand colors: KeeperAI Navy `#072436` (PANTONE 289 C) and KeeperAI Green `#10DE52` (PANTONE 2270 C).
- NEVER draw the primary action as a ghost button (white fill + Navy text). That is the
  secondary-action shape; using it for the one forward action on a screen erases the hierarchy. Measured: a multi-select
  question's confirm button — the only way forward on that screen — was drawn as a ghost.
- Primary CTA is ALWAYS Green `#10DE52` fill with NAVY `#072436` text
  (white text fails contrast at 1.81:1; Navy passes at 9.07:1). Changed 2026-09-07 (OPEN-12, option 2) — Green was
  previously excluded from CTA because the brand defines it as "confirmed / completed / resolved", the same semantics
  as a completed To Do in the call lifecycle (§3); that conflict was not resolved, it was knowingly overridden, and it
  matches what Figma already draws (Figma's own `#00E235` + white is not canonical — recommend Figma move to the
  official `#10DE52` + Navy pairing). The mitigation: completed/success feedback MUST use a soft tint pairing
  (`#00734F` text on `#E7FCEE`, 5.49:1), NEVER the solid `#10DE52` block. Focus ring stays
  2px Navy regardless — a Green ring measures 1.81:1 on white, under the 3:1 non-text contrast minimum.
- Destructive actions use Red `#FF5277` fill with NAVY text (not white), and only alongside
  the two-button confirmation modal. Measured: white on that red is 3.12:1 (fails AA), Navy is 5.12:1 (passes).

- NEVER pair two palette swatches without computing contrast. The obvious combinations fail:
  Green 04 `#00865F` on Green 10% `#E7FCEE` is 4.27:1, `#6B7280` on `#FEF3F2` is 4.45:1, white on Red `#FF5277` is
  3.12:1. Use `#00734F` (5.49:1), `#4B5563` (6.95:1), Navy on Red (5.12:1). Body needs 4.5:1; report the number.

## 5. Defensive Engineering & Safety
- Device font size: never cap it (`maxFontSizeMultiplier`, `allowFontScaling={false}`) and never change the default
  design. Adapt only when fontScale > 1 (two-line names, wrapping rows, taller fixed bars). Check 1.3x and 1.6x.
- Never put `flex:1` on text stacked in a column: on Android (Yoga) the column spreads apart and the web preview
  hides it. `flex:1` is for text directly in a row.
- Currency inputs must safely strip commas before numeric parsing to prevent `NaN` bugs.
- API submission buttons MUST implement debounce and display loading spinners with `disabled` states.
- Any multi-field input screen must auto-save a local draft.
- A bottom composer MUST live inside the keyboard-avoiding layout flow. Resize to the visible viewport, reserve
  scroll-bottom inset equal to the composer, and include the safe area. NEVER pin an input with
  screen-level `position:absolute; bottom:0`. On Android use window resize; on iOS use keyboard avoidance with safe area.
- Verify on a real device: keyboard closed/open × empty/multiline input × panel minimized/expanded × tab switch.
  The composer, send action, focused field and last content item must remain visible in every state.
- Expo/dev tools, inspector controls, accessibility utilities and OS floating overlays are not product UI.
  Never reproduce them from a screenshot. Render no app-owned debug entry points in release builds or final QA captures;
  record unavoidable external overlays separately from app defects.

## 7. Layout Patterns & Density (§2)

  No fifth pattern.

- Tab bar: white, 53pt including the home-indicator margin, four destinations max, LIST screens only. Bottom fixed

## 8. Interaction States (§1.7)
- Attention motion is one eased pass of light around the input border (cubic in-out, 1.6s), repeated as is. Never
  linear, never a breathing or pulsing ring, never layout properties. Hide while typing; none under reduce motion.
  Raise its layer so siblings never clip it.
- Never invent a state color. Step down the existing neutral ladder:
  there is no hover on touch: rest → pressed (surface `#F3F4F6` → `#E5E7EB`; primary Navy →
  `#04161F`) → selected → disabled.
- Never bind anything to hover. Selected: Figma fills segment chips `#28272F` (OPEN-14); tabs use a 2pt `#00CC46`
  underline. No swipe-to-delete and no long-press actions.
- Focus rings appear only for external keyboard / switch access, never on touch. Transition `background-color 120ms ease` — never layout properties.
- DISTINGUISH disabled from loading. Loading keeps the button's own background and adds a
  spinner; turning it grey mid-request looks broken.

## 9. Screen States — Empty / Loading / Error (§1.8)
- One question decides toast vs screen state: is there data to show on this screen?
  Yes → toast, leave the screen alone. No → replace the region with a screen state. Never a toast on an empty screen.
- Loading uses skeletons, not spinners (spinners only inside buttons and regions under 400px).
  Delay the skeleton by 200ms — flicker is worse than waiting. Mirror the real layout so
  nothing shifts on load.
- Empty state has THREE variants, never one: first-run (has a primary CTA), no-results (reset-filter only,
  echo the query back), all-clear (no CTA, KeeperAI Green allowed). Green on first-run reads as "done" — forbidden.
- Errors: 5xx/timeout → "Retry" primary. 403 → no retry button, it will not work. 404 → back to list.
- Never print stack traces or status codes. Print a request ID in `mono 11pt` instead.
- Error copy: what failed + what to do, two sentences max. Never "An error occurred". No apologies.
- Partial failure replaces only that region. A failed summary card must not blank the call list.
- NEVER render a spinner in an idle empty state. A ring that is not spinning reads as broken.
  The spinner exists only while something is actually pending.
- A step-by-step progress log is only for waits the user might walk away from — roughly 3s+.
  Attaching three log lines to a 1-2s computation manufactures a wait and violates §1.1. The threshold applies to the
  real duration; a prototype may compress it but must record the expected real duration in code.
- After a partial failure, do not auto-advance. Offer retry AND continue-anyway and let the
  user choose; advancing on its own buries the failed block above the scroll.

## 10. Layout Integrity (§1.9)
- One stat cell holds one value. Never `6건 합계 35,328,000원` in a single cell — the reader
  cannot tell which number is the point. Never mix kinds in one row (workload vs time estimate).
- Every block in a column MUST share one `left` and one `right`. Verify by measurement, not by eye.
- RESET `ol` TOO. `
    ` ships with `padding-inline-start: 40px`. Resetting only `ul`
  pushes that one row 40px inward and produces a visible misalignment. Reset `ul,ol,dl,dd,figure,fieldset`.
- Background fill is for the primary CTA only — one per screen. A selected option or toggle
  with the same Navy fill reads as a second primary action. Selected state = `#F3F4F6` + Navy text + weight 500.
- If empty space exceeds 40% of the first viewport, the screen-pattern choice (§2) is wrong, not the content.
- On a page that stacks several sections, move the fill instead of repeating it. One CTA per
  section means several filled buttons on screen at once; keep the fill on the step the user is on and demote the rest.
- Spacing carries hierarchy. Gap between groups must be at least 2x the gap inside a group.
  8px inside the option row and 6px before the primary CTA makes them read as one block — recoloring does not fix it.
- Controls in one row MUST share a right edge. Content-width options end at 439/545/633px — use `flex:1` or a grid.
- DELETE a widget once it is used — an answered choice card, a submitted upload card, an
  approved confirm card. Leaving it `disabled` pins the fill to a dead card. The chosen value already survives in the
  user's own message, the document, or the row. Keep a record-bearing block (an error) but strip its buttons and leave
  one result line. If removing the widget empties its message, remove the message too — a lone avatar is a blank bubble.
- Verify the single-fill rule by driving the whole flow and sampling `.btn-primary` every 60ms.
  Checking one state misses the rest.
- NEVER strip every `.hide` to "reveal all states" on a stateful app screen — that switches on
  panels which must be off and you end up measuring a screen that is not under test. Reveal-all is for static documents;
  on app screens drive the flow and measure at each state.
- Data-row bottom rules: use `box-shadow: inset 0 -1px 0` — a `border-bottom` turns a 72pt row into 73pt and breaks the
  row spec.
- Write it as sentences before building controls. Weight sliders, IF-THEN rows, JSON editors and
  automation levels can almost always be written as sentences instead: not `마진율 >= 25% AND 주문금액 >= 100만` but
  `백만 원이 넘는 큰 주문은 다른 일보다 먼저 잡습니다`. Inequalities, `AND`/`OR`, percentages and `P1` are developer
  notation — keep them out of user-facing screens. Absorb skill differences through how much data you
  take in and how dense the sentences get (3 cards for a novice, 5-7 for an expert) — not by changing the UI.
- When several cards of the same kind each carry an approve button, none of them gets the fill —
  six cards would mean six filled buttons. Card buttons stay ghost/quiet; the fill lives on the one primary action.
- Editing one item must update its title and its body together. Changing only the body leaves a
  card whose heading contradicts its text.
- NEVER reuse one block for two meanings — "cannot enable yet" and "the limit now in force".
  Once the condition is met, the untrue warning stays on screen. Change surface and copy together with the state.
- A width cap is allowed in exactly one place: an utterance unit (chat bubble, toast — the cap
  is what distinguishes the speaker; use pt/%, never `ch`, keep it at 86%+ of the container, and apply the line-fill rule
  inside the bubble). Nowhere else — screens are one column at 20pt margins.
- NEVER put a click target inside a sentence in a read-only document. An inline link's hit area
  cannot exceed `line-height` (~27px), so it can never meet the 44pt touch target. Put such actions in a
  separate action row.

## 11. What "Intercom layout" means on the phone (§2)
- One column of white cards floating on the grey page background (`#F1F3F5`), radius 16pt, 20pt
  side margins. The background must remain visible around the cards — do not bleed cards edge to edge and separate
  them with lines alone.
- No side navigation. Navigation is the 4-item bottom tab bar (white, dark labels, active `#00CC46` — OPEN-13) plus
  back arrows. NEVER fill the tab bar or a header with a brand colour; the dark in-call overlay
  follows the OS call screen and is the one exception.
- Intercom is tight. A row is 72pt because it carries five things (direction, name, subtitle,
  score, time); inside a card everything is packed. Only the space between sections is generous
  — a label (오늘 / 어제) plus a large gap separates blocks. Tight rows, wide section gaps: that is the rhythm.
- Sections are separated by their heading plus a rule above it — not by cards, and with
  no eyebrow label above the heading. Meta that survives the delete test goes on the same line
  as the heading, right aligned — but never a count of things already on screen (§1.10).
  No decorative square, dot, or icon in front of either.

## 12. UX Writing (§1.10)
- NEVER join label fragments with a dash. Not `다음 — 질문 세 개` but `질문 세 개 답하기`.
  A button is one action phrase. Not `대성식자재 — 식자재 대량 납품` but `대성식자재 · 식자재 대량 납품`.
- Use the middle dot `·` for enumeration and qualification. Never `—`, `–`, or `--`.
  Only when every fragment is needed: run the delete test on each fragment after a `·` and drop it, dot included,
  if nothing is lost. Not `키퍼 AI 추천 · 지금 먼저 할 일` but `지금 먼저 할 일`; not `2번 전화했어요 · 아직 회신 전` but `2번 전화했어요`.
- Sentences assembled from data must pick Korean particles by the final consonant of the inserted word. A fixed
  `{name}는` yields `미소분식는`. Final consonant present → `은·이·을`, absent → `는·가·를`; test with
  `(code - 0xAC00) % 28 !== 0`. This was caught by measurement, not by eye.
- A button says what happens when you press it. Do not append the step number or the next screen's name —
  the secondary list already shows that.
- Button wording and its result toast must use the same verb: press `발송하기`, the toast says `발송했습니다`.
- No apologies, no exclamation marks, no system jargon.
- Never assert an AI estimate: no due chips (`기한 지남`, `오늘까지`) inferred from keywords. Show the To Do text as
  spoken; use the estimate only for ordering.
- Same data, same text everywhere: never rewrite a To Do label in a card, alert or summary. A slot named
  "…할 일" shows the task itself, never a reason such as `2번 전화했어요`.
- Chat quick requests are what the owner asks the AI (`회신 문구 만들어줘`), not feature names.
- Scope: copy visible in the product — buttons, labels, headings, help text, toasts, errors. Not spec prose.
- On the phone the list row IS the card (72pt). Do not nest cards inside cards; sections are labels, not cards.

  • 320px에서 채움 9건 · 가로 넘침 5건 — 이번에 넣은 「측정 폭은 셋(1440 · 320 · 최협)」 규칙이 드러낸 것이다. 원인은 규격끼리의 충돌이다 — §0.4는 배지 · 태그 · 칩에 nowrap을 기본 탑재하라고 하는데(금지 #02 방지책), 320px에서는 칩 하나가 화면보다 넓다(칩 목록 콘텐츠 388px / 박스 242px). 셋 중 하나를 골라야 한다 — ① 좁은 폭에서만 칩 줄바꿈을 허용(금지 #02 재발 위험) ② 지원 하한을 375px로 올리고 측정 폭 규칙을 수정 ③ 칩 문구를 짧게 줄인다(내용 변경). 1440px에서는 전 항목 0이다.
  • 목차 열 폭 260px — 웹 문서 규격의 목록 열(280px)과 다르다. 이 페이지는 웹 문서라 모바일 규격의 대상이 아니다.

  • §1.4 한글 양수 자간 — 표 헤더 thead th에 letter-spacing:.06em(0.66px), 금지 항목 번호 .inc-id에 .04em. 한글을 담는 요소였다. 전수 30곳 → 0으로 고쳤다. §0.4에 "한글 양수 자간 0곳"을 넣어 두고 정작 이 페이지가 어기고 있었다.

  • §0.4 viewport 누락 — 체크리스트가 <meta name="viewport"> 존재를 요구하는데 이 페이지에 없었다. 에뮬레이터는 375px 로 그려 줬지만 실제 폰은 980px 로 렌더했을 것이다 — 「375px 실측 통과」 보고가 실기기에서는 거짓이었다. 넣었다.
  • §1.10 제목 위 라벨(eyebrow) — 절 제목 8개 위에 §1 · CONSTITUTION 같은 영문 라벨, 감사 절 위에 날짜 라벨, 표지 제목 위에 이름까지 class="eyebrow"인 라벨. 11곳. 절 번호는 제목 안으로 넣고 영문 라벨은 지웠다. 표지 라벨은 제목 아래 바이라인으로 내렸다. 조항 번호(1.3)는 제목 옆이라 대상이 아니다 — 실측으로 갈랐다.
  • §1.10 제목·라벨의 대시 — 작업 순서 — 이 순서로만처럼 제목 6개 · 라벨 4개가 대시로 이어져 있었다. 10곳 전부 문장이나 괄호로 고쳤다. 규칙의 적용 범위 주석에 「규격 문서의 서술문은 대상이 아니다」라고 적어 놓고 제목과 라벨은 서술문이 아니다.
  • §1.9 텍스트 세로 붕괴 — eyebrow 를 고치려고 넣은 flex-wrap:nowrap이 만든 것이다. 번호와 배지는 줄지 않으니 미결 항목 제목이 감소분을 전부 흡수했다 — 헤더 182px에서 제목 47px, 152px에서 17px(12줄), 122px에서 0px(14줄). 규 격 의 적 용 범 위로 흘렀고 가로로 85px 넘쳤다. 번호 27곳을 제목 안으로 옮겨(.sec-no .rule-no .inc-no .open-no) 형제를 없애고, 제목에 최소 폭 12em을 줬다. 고치면서 새 위반을 만들었고, 1440과 375만 재고 통과로 보고했다 — §0.4에 「측정 폭은 셋」을 넣었다.
  • §1.10 플레이스홀더 잘림 — §1.9 단차 수정이 만든 것이다. 입력 상자를 행 높이(40px) 한 줄로 묶었는데 안내 문구는 그대로 길었다. 375px에서 상자 안쪽 151px · 문구 234px → 두 줄이 되고 둘째 줄이 잘려 됩니다가 반쪽만 보였다. 자동 높이는 입력값만 재므로 플레이스홀더에는 반응하지 않는다. 긴 안내는 카드로 옮기고 플레이스홀더는 짧은 라벨 하나(말씀해 주세요)로 통일했다. 규격끼리 값을 강제한다는 것을 규칙에 적었다 — 세 번째 충돌이다(nowrap↔짜부라짐, 최소 폭↔넘침, 행 높이↔글자 길이).
  • §1.4 서체 1종 — (?) 버튼 14개가 브라우저 기본 서체였다. 폼 컨트롤은 서체를 상속하지 않는다 — button{font-family:inherit}를 리셋에 넣었다. 조항 번호 .rule-id의 .04em 자간도 0으로. 숫자 라벨은 라틴 대문자가 아니다.
